# v0.1 implementation addendum

25 October 2026. This is the explicit set of clarifications used by compiler 0.5.0.
The original specification and vision remain unchanged beside this document. Read
this addendum with the original specification; it resolves the gaps listed below.
Compiler release numbers and language-specification versions are independent.

## Ownership of aggregates

A record owns every linear leaf reachable through its fields. Moving a field
invalidates that field and whole-parent uses on the selected family, while leaving
unmoved siblings available. Moving the parent invalidates all children, including
non-linear metadata. Field reassignment is outside the immutable core.

A variant, including Option<T>, is linear if any alternative contains linear data.
It is one sealed obligation until transferred or consumed by a decision. A decision
consumes it on its input family and introduces the active payload obligations on
the corresponding outcome family. Non-linear variants are reusable. Record fields
containing variants follow the same place rules; variants are destructured by
`delta`, not by field projection. Recursive types remain excluded.

Primitive borrow parameters borrow named places for the entire synchronous
invocation. Parent/child places overlap; sibling places do not. Shared borrows may
overlap each other. A consuming access conflicts with an overlapping borrow or
another consuming access anywhere in the invocation's arguments, including nested
constructors. Non-linear argument reads occur in source argument order.

Resource-containing temporaries may be transferred or decided whole. They must be
bound before projection or borrowing, so remaining obligations have named places.
All selected outer obligations enter a tail loop through explicit parameters.
These conservative restrictions are part of this implementation profile, not claims
of a complete Rust borrow checker. There are no first-class references or destructors.

Ownership is type- and path-based. A known empty constructor of a linear variant
still requires a transfer or decision. The checker does not refine its ownership
based on constant constructors. Decision arms remain exhaustive even for constants.

## Constructors and inference

`Some(value)` infers Option<T>. `None` requires an expected Option<T> from a typed
constructor field, call/exit argument or loop argument. Expected types flow into
nested constructors. Bare `x := None` or `x := Some(None)` without such a context
is an inference error. Local type annotations and backward inference are deferred.

Qualified builtin names are `Option.Some` and `Option.None`; generic type arguments
are supplied by context rather than expression syntax. A manifest's own Some/None
constructor retains priority over the short builtin name. A value binding retains
priority in a value expression. Qualified variant arms accept `Type.Constructor`;
Option arms accept `Option.Some` and `Option.None`. Both spellings identify the same
arm, so listing a short and qualified spelling of one alternative is a duplicate.
Primitive/region outcome arms remain unqualified.

## Pure operations and primitives

v0.1 has no additional mandatory catalogue of pure builtins. Literals, constructors,
projections and the specified logical/comparison operators are the entire pure
expression core. Other operations are declared primitives or single-exit regions
and are invoked through delta, as permitted by §20. Modular arithmetic builtins
are optional and are not supplied. Checked arithmetic uses explicit outcomes.

Manifests are contracts, not implementations. Every valid manifest operation is
supported by the scripted execution harness. Live adapters are supplied for the
specific contracts documented in language-reference.md. A missing or incompatible
live adapter is a host error, never an invented language outcome or undefined edge.
User primitive names do not automatically link arbitrary foreign functions.

## Backend and process boundary

The native pipeline is checked graph → generated Rust control flow → LLVM IR →
executable. Regions become functions, selectors become branches, and loops become
native loops. Rust supplies aggregate storage and LLVM integration; the executable
does not contain the graph interpreter. This is an implementation choice within
§16's backend-independent semantics, not new source syntax.

The small process harness accepts an entry region and arguments. It prints the
returned outcome; any declared outcome is a normal process completion (status 0).
Malformed arguments, adapter failures outside their contracts, build failures and
optional fuel exhaustion are host failures (nonzero status). An explicit `--fuel`
limit is a testing facility, not a proof or change to language termination semantics.

The live file adapter uses C stdio streams. Open maps absence to NotFound and other
open errors to Denied; read returns all remaining bytes or Failed; fclose consumes
the stream on either result. Source programs must close or transfer handles. At the
process boundary, escaped handles belong to the harness; process shutdown/host-error
cleanup is outside source-language traces and performs best-effort host cleanup.
Resource identity contracts supplied by a script remain trusted.

## Provenance and verification

Identities are stable within a compilation and transformation, not across source
edits. Provenance retains definition region, location, optional decision-site name,
and distinct call identities with readable call contexts. Completion instructions
explicitly map each internal exit site to the caller outcome atom and payloads.

The transformation verifier checks identities, references, expression/call types,
arm exhaustiveness, and loop/completion targets. It is not an independent proof of
the source checker's path coverage or linear-resource analysis. Differential tests
provide additional evidence for preservation of traces and ownership behavior.

## Deferred scope

Full Rust Copy/Clone/Drop semantics, escaping/mutable references and lifetimes,
recursion, concurrency, mutation, modules, package management, graph editing,
source extraction, persistent identities across edits and richer proof inference
remain future work. They are not required for this v0.1 implementation profile.
